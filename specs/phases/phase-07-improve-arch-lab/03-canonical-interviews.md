# Phase 7.3 — Canonical Interviews

## Goal

Make the **interview** challenge a classic system-design problem (a URL shortener, a rate limiter, a
news feed), chosen from a fixed list in the catalog, with no study session and no folder involved.
The **practice** challenge keeps its role: train one concept from a session, in a folder with the
Architecture Lab enabled ([7.1](01-arch-lab-per-folder.md)).

This follows a comparison with a market tool (a guided practice of "Design a URL Shortener Like
Bitly"). There the system comes first and each topic is one deep dive among several: caching is one
of three questions about redirects, not the whole exam. Here the topic of the session decides the
interview, so it ends up a concept question dressed as a product.

## Findings that shape the design

- The two interviews generated so far are both "product recommendations". Their mandatory criteria
  and most of their challenge criteria are about caching ("Estratégia de Cache", "Invalidação e
  Atualização", "Tratamento de Cache Miss e Thundering Herd"), because the session topic was cache.
  The system is a pretext for the topic.
- A real interview does not depend on what the candidate studied last. Tying it to a session also
  raised the question of which folders may generate one; a session-free interview removes it.
- Interviews generated by the model drift: the scale changes from one generation to the next and the
  model invents the system. A fixed list with a fixed scale per difficulty removes both.
- The catalog already supports challenges with no session: `SourceSessionID` is nullable, and
  [ADR-005](../../decisions/ADR-005-exercise-engine.md) already defines the standalone context.
- The Progress screen ([5.1](../phase-05-progress/01-progress-dashboard.md)) counts the challenges
  linked to a session. A canonical interview has no session, so its results will not appear there.
  This is a known consequence, listed in the out of scope.

## Decisions

1. **Two kinds, two entry points.**

   | | Practice | Interview |
   |---|---|---|
   | Starts from | a session in a folder with the lab enabled, plus the concept the user types | the catalog, a fixed list of problems |
   | Depends on a session | yes | no |
   | Content | one focused scenario, lean rubric, no time limit, starter diagram | a classic system, full rubric, time limit by difficulty |

2. **The problem list lives in code.** A `CanonicalProblem` is trusted data shipped with the app:

   ```go
   type CanonicalProblem struct {
       ID    string                // stable slug, e.g. "url-shortener"
       Name  LocalizedName         // {EN, PT}, shown as the challenge title
       Core  []string              // English; what the system must do, 2 to 4 lines
       Scale map[Difficulty]string // English; the load for each difficulty
   }
   ```

   `CanonicalProblems()` returns the list in a fixed order and `FindCanonicalProblem(id)` looks one
   up. The first version has the six problems of the section below. Worked example, the URL
   shortener: `Core` = "Create a short URL from a long one", "Optionally choose a custom alias and
   an expiration", "Redirect a short URL to the original"; `Scale` = beginner "10 million stored
   URLs, 1 million daily users", intermediate "1 billion stored URLs, 100 million daily users",
   advanced the same with several regions. A test asserts every problem has a name in both
   languages, at least two core lines and a scale for each of the three difficulties.
3. **Code decides who the system is; the model writes the statement.** The model never chooses the
   problem, the title or the scale. Code sets the title (the problem's name in the assistant
   language), the topic and the canonical id. The model receives the problem's core lines and the
   scale for the chosen difficulty and writes the scenario, the requirements, the constraints, the
   objectives and the challenge criteria. The quality rules of [7.2](02-generation-quality.md)
   apply: shares and floor of the rubric, the criteria cap for the difficulty, the short beginner
   statement and the target-not-mechanism rule. Since the title comes from code, it cannot name a
   solution.
4. **One challenge per problem and difficulty, generated when first used.** Nothing is generated
   ahead of time: not at install, not after a reset, not when the catalog opens. The first **Start**
   on a problem and difficulty with no challenge generates it (one LLM call), stores it and goes on
   to start the exam. From then on it is reused with no call. The same
   progress, **Cancel** and failure behavior of the catalog's generation applies
   ([3.7](../phase-03-architecture-lab/07-challenge-catalog-ui.md) decision 8,
   `CancelChallengeGeneration`, one generation at a time); on failure nothing is stored and the user
   retries.
5. **The context is small.** The generation receives the problem, the difficulty and the profile
   (focus area, experience level, assistant language), escaped as everywhere. It receives no session
   topic, summary or notes.
6. **Difficulty is chosen when starting.** A dialog on **Start** asks for the difficulty,
   preselected from the profile's experience level (an unknown level is Intermediate). Each option
   shows that difficulty's state for the problem ("Not generated", "Not started", "Completed" and so
   on, from [3.6](../phase-03-architecture-lab/06-completion-rules.md)). The time limit comes from
   `DefaultTimeLimit` and the defense keeps its 5 questions, both unchanged.
7. **Persistence.** `challenges` gains `canonical_problem_id TEXT NOT NULL DEFAULT ''`, filled for
   the interviews of this spec and empty for everything else. `source_session_id` stays empty,
   `origin` is `AI_GENERATED` and `topic` is the problem's name. A partial unique index
   `(canonical_problem_id, difficulty) WHERE canonical_problem_id <> ''` holds the "one per problem
   and difficulty" rule at the database level, so two generations racing can never store two.
   The challenge keeps the language it was generated in, like any other
   ([3.20](../phase-03-architecture-lab/20-lab-language.md) decision 7).
8. **The catalog gets two tabs.**
   - **Interview:** one row per problem, in the list's order. A row shows the problem's name in the
     profile's language, a one-line description, how many difficulties are generated, the total
     attempts and a **Start** button, plus **History** when there is any finished attempt. Like any
     row, it never shows the scenario or the rubric
     ([3.7](../phase-03-architecture-lab/07-challenge-catalog-ui.md) decision 3). The tab lists only
     canonical problems.
   - **Practice:** the current list of practice challenges with its filters, counts and
     **Generate practice**.
   The counts and filters of 3.7 apply per tab.
9. **The generation dialog is practice-only.** It loses the kind selector. It lists the sessions of
   enabled folders ([7.1](01-arch-lab-per-folder.md)), asks for the practice goal (required) and the
   difficulty, as in [3.18](../phase-03-architecture-lab/18-practice-challenges.md).
10. **The chat offer is practice-only.** The study prompt asks the model to offer a practice
    exercise, and the offer card loses the kind selector and asks for the goal. A request for a full
    interview in the chat gets a normal reply that points to the catalog. In a disabled folder there
    is no offer ([7.1](01-arch-lab-per-folder.md)).
11. **No earlier interviews are kept.** The interviews generated from sessions before this spec are
    test data, and the user clears them with the reset of the local data in Settings
    ([1.13](../phase-01-desktop-mvp/13-reset-local-data.md)), which deletes every Architecture Lab
    row (and also the sessions, folders and knowledge). This spec adds no handling for them: an
    interview with no canonical id is listed in neither tab. `GenerateChallenge` no longer accepts
    the interview kind.
12. **Attempts are standalone and the rest is unchanged.** An interview attempt has no
    `SessionExerciseID`. The exam, the hints, the evaluation, the 5-question defense and the result
    view work as they do today. **History** on a problem lists the finished attempts of all its
    difficulties, newest first, with the difficulty shown on each; opening one is the same result
    view.
13. **Cost.** One generation call per problem and difficulty, the first time it is started. Every
    later start of it makes none.
14. **No data compatibility to keep.**

## The first six problems

URL shortener, rate limiter, news feed, chat application, notification service and ticket booking.
The list is data in code, so changing or growing it is one place to edit and its test.

## Decisions taken in review

- **The initial list is the six problems above.** The list is data in code, so it can change later
  in one place.
- **One catalog row per problem**, with the difficulty chosen in the Start dialog (decisions 6 and
  8), not one row per problem and difficulty.
- **Earlier interviews are not kept** (decision 11).

## Changes to earlier specs

- **3.1:** decision 1 (a challenge always has a source session) no longer holds for an interview;
  `source_session_id` is empty for it. `Challenge` gains `CanonicalProblemID`. `Create` keeps
  requiring a session; the canonical path creates the challenge without one.
- **3.6.1:** generation from a session is practice-only; `GenerateCanonical` is new.
- **3.7:** the catalog has the two tabs of decision 8; the generation dialog is practice-only.
- **3.13:** History from a problem spans its difficulties.
- **3.14:** the offer is practice-only.
- **3.18:** the kind selector disappears from the dialog and the offer; interview is no longer the
  default kind of a generated challenge.
- **7.1:** its gate then applies to practice only.

## Domain and application

`internal/domain/exercise/`: `CanonicalProblem`, `LocalizedName`, `CanonicalProblems()`,
`FindCanonicalProblem`, `ErrCanonicalProblemNotFound`, and `Challenge.CanonicalProblemID`.

`internal/application/exercise`:

```go
func (s *GenerationService) GenerateCanonical(ctx, problemID string, difficulty Difficulty) (Challenge, error)
func (s *CatalogService) ListCanonicalProblems(ctx) ([]CanonicalProblemItem, error)
```

- `GenerateCanonical`: find the problem (`ErrCanonicalProblemNotFound`); if a challenge already
  exists for that problem and difficulty, return it with no call; otherwise build the prompt from
  the problem, the difficulty and the profile, call the model with no transaction open, parse, apply
  the rules of [7.2](02-generation-quality.md), set title, topic and canonical id from code, and
  store the challenge and its first rubric version in one transaction
  ([3.6.1](../phase-03-architecture-lab/06-01-challenge-generation.md) decision 6), with an empty
  source session. The unique index is the backstop for a race.
- `GenerateChallenge` (from a session) loses the interview kind: an interview request fails with a
  clear error and stores nothing.
- `CanonicalProblemItem{ID, Name, Summary, Difficulties []DifficultyState, Attempts, HasHistory}`,
  where `DifficultyState` carries the difficulty, whether a challenge exists, its challenge id and
  its derived status. Status is derived by `DeriveProgress`, never in the frontend.
- `exercise` imports neither `study` nor `folder`; the profile comes through the existing
  `ProfileReader` port.

## SQLite

Guarded migration:

```sql
ALTER TABLE challenges ADD COLUMN canonical_problem_id TEXT NOT NULL DEFAULT '';
CREATE UNIQUE INDEX idx_challenges_canonical
  ON challenges(canonical_problem_id, difficulty) WHERE canonical_problem_id <> '';
```

The challenge repository reads and writes the column and exposes a lookup by canonical id and
difficulty.

## Desktop bindings and frontend

- Bindings in `internal/interfaces/desktop/exercise.go`: `ListCanonicalProblems()` and
  `GenerateCanonicalChallenge(problemId, difficulty)`, thin, an error code per sentinel. The
  existing generation binding drops the interview kind. `wailsjs` regenerated.
- `ArchitectureLabScreen`: the two tabs; `canonical-problem-row.tsx`; the Start dialog with the
  difficulty options; the generation progress, cancel and error states reused from the existing
  dialog; the practice dialog without the kind selector; the offer card without it.
- `lib/exercise.ts` wrappers and the DTO types.
- All new Architecture Lab text lives in the `lab` namespace, in `en.ts` and `pt.ts`
  ([3.20](../phase-03-architecture-lab/20-lab-language.md)); the problems' names come from the
  backend in the profile's language.

## Acceptance Criteria

- The catalog opens on two tabs; the Interview tab lists the six problems with no network call and
  no generation, also right after a reset of the local data.
- Starting a problem and difficulty that has no challenge generates one, shows progress, can be
  cancelled, and on failure stores nothing and offers a retry; on success it starts the exam.
- Starting the same problem and difficulty again makes no LLM call and opens the same challenge.
- The challenge title is the problem's name in the assistant language and was not written by the
  model; its scale matches the problem's scale for that difficulty.
- Two concurrent generations for the same problem and difficulty store one challenge.
- A generated interview has no source session, a `canonical_problem_id`, and no `SessionExercise`.
- The Practice tab and the practice generation dialog work as in 3.18 and [7.1](01-arch-lab-per-folder.md), with no
  kind selector; a request for an interview through `GenerateChallenge` fails and stores nothing.
- The chat offers a practice exercise only, and a request for a full interview gets a normal reply.
- The Interview tab lists only the canonical problems; an interview without a canonical id is not
  listed.
- History from a problem lists the finished attempts of its difficulties, with the difficulty on
  each, and opens the usual result view.
- `go test -race ./...`, coverage ≥ 80%, `make mutation-go` clean for the changed
  application/domain code, lint and vulnerability checks, and the frontend tests, coverage, lint,
  typecheck, `npx prettier --check .` and Stryker on the changed files pass.

## Out of scope

- A guided mode with steps (requirements, entities, API, design, deep dives), a per-step tutor tip
  and suggested time.
- A clarifying-questions channel with an interviewer, and making the learner write the
  non-functional requirements. Both are one increment of their own: the statement keeps its
  non-functional requirements here.
- Deep dives defined in each problem's data. The defense keeps choosing its questions from the
  rubric ([3.12](../phase-03-architecture-lab/12-architecture-defense.md)).
- Showing canonical interview results in Progress, which counts session-linked challenges.
- More than the first six problems, user-defined problems and regenerating a stored challenge.
- Voice answers, a level selector outside the Start dialog, and a "study this gap" action from the
  result.
