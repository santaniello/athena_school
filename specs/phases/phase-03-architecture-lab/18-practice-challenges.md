# Phase 3.18 — Practice Challenges

## Goal

Let the user choose what kind of challenge to create. Today every generated challenge reads like a
job interview ("design an e-commerce system"), even at the beginner level. This phase adds a second
kind, **practice**, for training one specific concept: a product API that calls a slow price API,
a cache-aside mechanism, and so on. The existing behavior is the **interview** kind.

## Decisions

1. **Two kinds.** `INTERVIEW` is what exists today: a broad product scenario, a time limit and the
   full rubric. `PRACTICE` trains one concept: a short, focused scenario, no time limit and a lean
   rubric limited to that concept.
2. **`Kind` is not `Type`.** `Type` says which lab a challenge belongs to (`ARCHITECTURE`). `Kind`
   says how the challenge is shaped. They are separate fields.
3. **The user asks for the kind when creating.** The catalog dialog ([3.14](14-ai-challenge-generation.md))
   and the chat offer card get a kind selector next to the difficulty. Interview stays the default.
4. **Practice needs a goal.** For a practice challenge the user writes what they want to practice,
   in free text. It is required. The dialogs show suggestion chips taken from the session's topic
   and goal, with no extra model call. The goal goes to the model inside an escaped
   `<practice_goal>` tag and is treated as untrusted data, like the other learner fields.
5. **No time limit.** A practice challenge has `TimeLimitMinutes == 0`, meaning untimed. The value is
   valid only for `PRACTICE`; `INTERVIEW` still requires 1 to 180. An attempt on an untimed
   challenge has a zero `Deadline`, never expires and is never discarded for being late. The lab
   shows no countdown and the cards show "No time limit".
6. **Lean rubric.** A practice rubric has no base criteria: only 1 to 3 criteria about the practiced
   concept, weights scaled to 100 as usual. Its `BaseVersion` is `none`. Editing the rubric of a
   practice challenge never adds the base criteria back.
7. **A practice challenge is never reused.** It depends on the goal the user wrote, so the offer
   flow ([3.14](14-ai-challenge-generation.md) decision 8) reuses an existing challenge only when it
   is an interview of the chosen difficulty.
8. **Unchanged on purpose:** the diagram answer, the evaluation, the tutor hints and the oral
   defense work the same for both kinds. A lighter defense for practice is a follow-up.
9. **Existing challenges are interviews.** The migration adds `kind` with default `INTERVIEW`.
10. **Out of scope:** a kind filter in the catalog, kind-specific hints or defense, concept
    suggestions generated by the model, manual creation of a practice challenge.

## Changes to earlier specs

- **3.1:** `Challenge` gains `Kind`; `TimeLimitMinutes` may be 0 for `PRACTICE`.
- **3.2:** a rubric may have no base criteria when its challenge is a practice.
- **3.3:** `ChallengeAttempt.Deadline` may be zero; `Expired` is false for a zero deadline.
- **3.14:** `GenerateChallenge` and `Accept` take the kind and the practice goal.

## Verification

Unit tests per layer (domain, prompt, parse, services, SQLite, desktop, frontend), then the real
app: create a practice challenge about "cache aside" and check the short statement, the 1 to 3
criteria, no countdown and a working submit and evaluation; create an interview and check nothing
changed.
