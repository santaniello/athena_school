## [Unreleased]

### Changed
- Phase 2 Knowledge Engine specifications now add persistent provenance, exact/semantic duplicate detection, human-approved knowledge reconciliation, and immutable revision history. `message_sources` moves from Phase 3 into Phase 2 so resumed answers retain their original RAG sources; Knowledge Items in every lifecycle state are indexed for duplicate checks while RAG remains approved-only; Phase 7's graph now reuses ID-backed relations instead of concept-name keys. Added specs 2.9–2.12 and renamed 2.8 to [08-knowledge-item-indexing.md](specs/phases/phase-02-knowledge-engine/08-knowledge-item-indexing.md)
- Phase 2 (Knowledge Engine) specs rewritten against the current codebase (`specs/phases/phase-02-knowledge-engine/`, `specs/phases/README.md`, `specs/Planning.md` §Fase 2). The extraction trigger moved from "after each study session" to an explicit "Extract knowledge" action, because the study domain has no session-end concept (`Session` has no `EndedAt`, there is no `End` use case) and reintroducing one would disturb a stable area; extraction now returns unpersisted candidates so "Ignore saves nothing" is literally true. The `KnowledgeItem` lifecycle rule is pinned to a pure `TransitionTo` with no `UpdateStatus` on the repository, making it non-bypassable; `knowledge_chunks` gained `topic`/`status`/`item_id` (without them `SearchFilters` is unimplementable) and a companion `ingested_files` table that answers where the dedup mtime lives; `VectorStore` gained `ScoredChunk`/`Remove`/`Len`; RAG context is injected as a second `system` message so `buildSystemPrompt` and its tests are untouched, behind a `knowledge.Retriever` port rather than a concrete dependency. The initial rewrite split delivery into two demonstrable slices (2.1→2.2→2.6→2.7, then 2.3→2.4→2.5→2.8); specs 2.9–2.12 now form the third increment. A review pass then closed the contradictions the first draft still carried: `Search` normalizes the query as well as the stored vectors (a dot product is only cosine when both sides are unit length), re-importing a changed file evicts its old vectors from the in-memory store and not just from SQLite, an empty vector store no longer short-circuits past the `strict-notes` mode check, `RejectAllDrafts` deletes instead of pretending rejection is a status transition, the 8-item extraction cap is enforced in Go rather than only requested in the prompt, headingless markdown falls back to paragraph splitting instead of ingesting nothing, and `ingested_files` keys on the embedding model so changing it re-embeds automatically
- `README.md` CI/CD section: the note claiming the repository is private and that no job is a required status check is obsolete — the repo is public and all five CI jobs are wired as required status checks on `main` with `strict: true`
- `mutation-frontend` CI job: PRs now run Stryker only against files changed vs. the base branch (`git diff` + `--mutate`); pushes to `main`/`develop` run the full suite in incremental mode (`incremental: true` in `frontend/stryker.config.mjs`), with `reports/stryker-incremental.json` cached per branch across runs — cuts the ~30min full-repo mutation run on every PR down to just the touched code

### Fixed
- React `act()` warnings in the two onboarding tests, the only stderr output left in the frontend suite. Bisecting produced a minimal repro: focusing a text input and *then* opening a Radix Select warns, while the reverse order does not. Opening a Select makes Radix pull focus into its listbox, and when an input holds focus that blur/focus pair lands outside React's act scope under jsdom, so `SelectItem`'s `onFocus` (`@radix-ui/react-select` `index.mjs:866`) sets state un-acted. Both tests now pick options through a `pickOption` helper that drops focus before opening the trigger — what a real browser's click does on its own — and then waits for the trigger to show the chosen label, which also asserts the pick took effect, something clicking an option alone never verified. The suite now runs with no stderr at all
- Flaky frontend tests: `App > completes onboarding end-to-end` and `OnboardingScreen > moves to confirmation, saves, and completes onboarding` failed intermittently on a 5s timeout whenever the full suite ran in parallel, while passing in isolation. Vitest's 5s default was never sized for this suite — `App.tsx`'s deliberate 1.4s boot splash (`MIN_SPLASH_MS`) is paid by every end-to-end test before it can assert anything, and the onboarding flow adds a dozen real interactions across three Radix Selects on top, putting the slowest test at ~2.6s on an idle machine and well past 5s under worker contention. Raised `testTimeout` to 20s in `frontend/vite.config.ts` (a ceiling for detecting a stuck test, not a target) and switched the free-text form fields in both tests from per-character `user.type()` to `user.click()` + `user.paste()`, which cuts ~20% off the slowest test without losing coverage — the controlled inputs see the same change events either way, and Goals keeps `type()` since its TagInput commits on `{Enter}`
- Window opening minimised/unfocused on Linux (confirmed on Cinnamon/Muffin): `gtk_window_present` — what backs Wails' `WindowUnminimise`/`WindowCenter` — gets silently downgraded to a taskbar "demands attention" flash by focus-stealing prevention when the app is launched from a terminal instead of a desktop launcher, and toggling always-on-top hits the same wall. `main.go`'s `OnStartup` now shells out to `wmctrl -F -a "Athena"` (matched by the window's exact title, a literal so it satisfies gosec's G204 with no suppression, retried for a few seconds to survive slow window mapping), whose activation request carries the EWMH "pager" source indicator that these window managers do trust
